## How to explain this part (interview)
- All mutations reuse the HTTP routes via same-origin `fetch`; the UI adds no write path, so the server's 401/404/403 checks are the only authority. Hidden buttons are cosmetic.
- Each page calls `requireMemberPage`/`requireTenantPage` itself; layouts are not trusted because they don't re-run on navigation.
- Dates: business dates are strings formatted by splitting, never `new Date('YYYY-MM-DD')` (that shifts a day in New York). Instants use `formatToParts` with `timeZone: 'Asia/Kuala_Lumpur'` and are assembled by hand, so output is identical on server and any browser.
- Hydration: staff pages format on the server; client components get preformatted strings or fixed props (`defaultReceivedAt`). The portal formats only after its client fetch, so nothing date-related is server-rendered there.
- Record form: ringgit parsed with `parseRinggitToSen`; the `datetime-local` value is read as MYT and sent as `…+08:00`, independent of device TZ.
- Tenant portal reads through browser supabase-js in one embedded select; RLS is the boundary, no `.eq` filters as security. Phone update touches only `tenants.phone` (column grant).
- Slip links: a server action checks scope, then signs a 60 s URL with the user's own client, so Storage RLS also applies; the secret key never leaves the server.
- Seed regression: a Next-only import in a shared lib breaks scripts that run outside Next; such imports stay lazy.
